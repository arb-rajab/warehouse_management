# Dashboard filter dialogs and warehouse stock links

## Dashboard's custom-expiring-days field lives behind a FilterDialog, not a live `@change` input
`#dashboard-custom-expiring-days` used to be a bare `type="number"` input wired to `@change`, which fired a `router.get` on every native spinner click — rapid increment/decrement clicks each canceled the in-flight request from the previous click. It's now a `filterTriggerButtonClass` button (`expiringWindow.label`, SlidersHorizontal icon) that opens a `FilterDialog` containing a `FilterNumberField` (label `cellHighlight.expiresWithinDays`, reused rather than adding a near-duplicate string) and a `filterApplyButtonClass` submit button (`expiringWindow.apply`) — same "closed by default, edits don't reload until Apply" pattern as CellStatusLogs' filter dialog (see cell-log-filters.md). `submitCustomExpiringDays()` re-seeds the draft from `props.stats.expiring.custom.days` each time the dialog opens (`openCustomExpiringDaysDialog()`) and only calls `router.get` on form submit, then closes the dialog. Don't reintroduce a live `@change`/`@input` handler on this field — any request must be gated behind the dialog's explicit submit.

## The stale-within-days card is the same dialog-gated pattern, plus a deep-link into Cells map staleness
`#dashboard-custom-stale-days` mirrors the custom-expiring-days card exactly: `filterTriggerButtonClass` button (`staleWindow.label`, SlidersHorizontal icon) → `FilterDialog` → `FilterNumberField` (label `cellHighlight.staleAfterDays`, reused from the Cells map's own stale filter rather than a near-duplicate string) → `filterApplyButtonClass` submit (`staleWindow.apply`). `submitCustomStaleDays()`/`openCustomStaleDaysDialog()` follow the same re-seed-on-open, submit-only-on-Apply rule as expiring's — don't wire a live handler here either. Unlike expiring, the count/day pair for this card (`stats.stale`) has no fixed-window siblings (no "expired" equivalent for staleness), so it's its own `dashboard.stale` section with one tile.

Two deliberate departures from the general "no fixed stale threshold" rule in models.md, made for this one card specifically (see that file's "Stale pallets" section for the full reasoning): it has a real default (`BuildsDashboardStats::DEFAULT_CUSTOM_STALE_DAYS`, 21, from a `stale_days` query param — not a `Pallet`-level constant), and its tile's `href`/`query` (`stale_after_days: stats.stale.days`) links to the matching pallets list with `stale_after_days` the same way the expiring tile links with `expires_within_days` (validated by `FilterMatchingPalletsRequest`). Every place that submits a dashboard `router.get` (`submitCustomExpiringDays`, `submitCustomStaleDays`, `onProductIdsChange`) must keep sending both `expiring_days` and `stale_days` together, or switching one custom window silently resets the other back to its default.

## The inactive-in-warehouse card is a plain count tile, deep-linking into the products page's own filtered list
`dashboard.inactiveInWarehouse` is a single `DashboardStatTile` like every other dashboard stat (`stats.inactive_in_warehouse.count`, linking to `admin/products?inactive=true`) — it does not render its own per-product list. An earlier version rendered the products inline in the tile's `#footer` slot; that was removed once `Admin\ProductController::index()`'s `inactive` filter itself was redefined to mean the same "deactivated and in the warehouse" subset (see products.md), since the tile's link now lands on exactly the right filtered list — a second copy of that same list on the dashboard card would just be duplicated UI. If a future card needs an inline list again, `DashboardStatTile`'s `#footer` slot is still the established extension point (used by the expiring/stale cards for their filter dialogs) — but check first whether the target page's own filtered view already covers it, as it does here.

`BuildsDashboardStats::inactiveInWarehouse()` counts via the shared `Product::inWarehouse()` `#[Scope]` (`app/Models/Product.php`) — the same scope the products index's `inactive` filter applies — so the dashboard count and the list it links to can never disagree on which products match.

## The warehouse filter sits beside the product filter and rides every request
`FilterWarehouseSelect` (`#dashboard-warehouse`) follows `FilterProductSelect` in the header and reloads the page the same way (`router.get` of `dashboardIndex()`, `preserveState`, `replace`), with `filters.warehouse_ids` and `filterOptions.warehouses` as its model and labels. Every `router.get` on this page (`onProductIdsChange`, `onWarehouseIdsChange`, the two day-window dialogs) sends `product_id`, `warehouse_ids`, `expiring_days` and `stale_days` together, or changing one filter silently resets the others. The tiles carry `warehouse_ids` to the pages that filter by it (matching pallets, activity log) through `warehouseQuery`, next to `productQuery`; the low-stock and inactive tiles link to the products page, which has no warehouse filter, so they leave it out.

## The unplaced pallets card is a plain count tile opening the matching list with `unplaced=true`
`dashboard.unplaced` is its own section right after occupancy: one `DashboardStatTile` (`stats.unplaced_pallets.count`, `Truck` icon, `tone="warning"`) linking to `palletsIndex` with `unplaced: true` plus `productQuery` and `warehouseQuery`, like the pallet tiles around it. It has no day window, so no dialog. `BuildsDashboardStats::unplacedPallets()` counts `Pallet::unplaced()` through `forWarehouses()` (an unplaced pallet's warehouse is its receipt's) and `applyProductFilters()`, the same scopes the list's `unplaced` filter applies, and the mobile dashboard gets the same figure as `stats.unplaced_pallets.count`. The expired, expiring and stale cards include unplaced pallets (no `placed()`), because the matching list they open lists them; the occupancy tiles do not, since a cell state is a cell fact. Its Help text is the `unplaced` section of `Help/Dashboard.vue`; keep it, the `help.dashboard.unplaced` keys and the overview body in step with the card.
