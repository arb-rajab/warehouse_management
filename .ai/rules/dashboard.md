# Dashboard

## Dashboard's custom-expiring-days field lives behind a FilterDialog, not a live `@change` input
`#dashboard-custom-expiring-days` used to be a bare `type="number"` input wired to `@change`, which fired a `router.get` on every native spinner click — rapid increment/decrement clicks each canceled the in-flight request from the previous click. It's now a `filterTriggerButtonClass` button (`expiringWindow.label`, SlidersHorizontal icon) that opens a `FilterDialog` containing a `FilterNumberField` (label `cellHighlight.expiresWithinDays`, reused rather than adding a near-duplicate string) and a `filterApplyButtonClass` submit button (`expiringWindow.apply`) — same "closed by default, edits don't reload until Apply" pattern as CellStatusLogs' filter dialog (see pages-admin-cell-status-logs.md). `submitCustomExpiringDays()` re-seeds the draft from `props.stats.expiring.custom.days` each time the dialog opens (`openCustomExpiringDaysDialog()`) and only calls `router.get` on form submit, then closes the dialog. Don't reintroduce a live `@change`/`@input` handler on this field — any request must be gated behind the dialog's explicit submit.

## The stale-within-days card is the same dialog-gated pattern, plus a deep-link into Cells map staleness
`#dashboard-custom-stale-days` mirrors the custom-expiring-days card exactly: `filterTriggerButtonClass` button (`staleWindow.label`, SlidersHorizontal icon) → `FilterDialog` → `FilterNumberField` (label `cellHighlight.staleAfterDays`, reused from the Cells map's own stale filter rather than a near-duplicate string) → `filterApplyButtonClass` submit (`staleWindow.apply`). `submitCustomStaleDays()`/`openCustomStaleDaysDialog()` follow the same re-seed-on-open, submit-only-on-Apply rule as expiring's — don't wire a live handler here either. Unlike expiring, the count/day pair for this card (`stats.stale`) has no fixed-window siblings (no "expired" equivalent for staleness), so it's its own `dashboard.stale` section with one tile.

Two deliberate departures from the general "no fixed stale threshold" rule in models.md, made for this one card specifically (see that file's "Stale pallets" section for the full reasoning): it has a real default (`BuildsDashboardStats::DEFAULT_CUSTOM_STALE_DAYS`, 21, from a `stale_days` query param — not a `Pallet`-level constant), and its tile's `href`/`query` (`stale_after_days: stats.stale.days`) deep-links into the Cells map's `staleAfterDays` highlight filter the same way the expiring tile already deep-links `expires_within_days` — `CellHighlightSeed.staleAfterDays`, seeded server-side by `ShowCellMapRequest`'s `stale_after_days`, is no longer client-only (see lib.md/controllers-admin.md). Every place that submits a dashboard `router.get` (`submitCustomExpiringDays`, `submitCustomStaleDays`, `onProductIdsChange`) must keep sending both `expiring_days` and `stale_days` together, or switching one custom window silently resets the other back to its default.

## The inactive-in-warehouse card is a list, not just a tile — first of its kind on this dashboard
Every other dashboard section is a grid of `DashboardStatTile`s (a single number + label). `dashboard.inactiveInWarehouse` needed an actual list of products, so it reuses `DashboardStatTile` for the header count/link (`stats.inactive_in_warehouse.count`, linking to the products index with `inactive: true`) but renders the per-product list inside that same tile's `#footer` slot as a plain `<ul>` — no new shared list component, since this is still the only caller. Don't reach for `DashboardStatTile` alone to render a list of records; its `value` prop is a single number and its `#footer` slot is the established extension point (already used by the expiring/stale cards for their filter dialogs).

The count query (`BuildsDashboardStats::inactiveInWarehouse()`) is deliberately distinct from `FilterProductsRequest`'s `inactive` filter, which is occupancy-agnostic by design (see products.md) — this stat is `published = false AND` at least one row in `pallets`. Because `pallets.cell_id` is non-nullable and unique (see models.md/Pallet's docblock), every pallet row is inherently "in a cell", so no cell-state check is needed. The list itself is capped (`BuildsDashboardStats::INACTIVE_IN_WAREHOUSE_LIMIT`, 10) while `count` always reflects the untruncated total — don't let the list's `count()` diverge from the capped `get()` by reusing one query instance across both without cloning first.
