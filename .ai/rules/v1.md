# V1

## Box-count tracking: open() removes boxes too; boxes_count on logs is a snapshot, not a delta
`Product::$boxes_count` is a derived attribute backed by `wms_product_settings.boxes_count`, with `Product::DEFAULT_BOXES_COUNT` (50) when no setting exists; it is not a `products` column. `PalletActionService::store()` seeds `pallets.remaining_boxes` from it. `open()`/`removeBoxes()` decrement the count through the service's private `decrementRemainingBoxes()` helper, with a 409 `insufficient_boxes_remaining` when removal meets or exceeds what remains without `confirm_empty`.

The count is not decrement-only: `Admin\PalletController::update()` and accepted verification corrections through `CellVerificationService` use `PalletActionService::update()` to set `remaining_boxes` directly. Positive corrections may increase or decrease it without a log unless the product also changes. A zero correction requires `confirm_empty` and deletes the pallet through `emptyLockedPallet()` instead of storing a zero count.

`open()` takes an optional `boxes_count` (`ValidatesBoxesCount::optionalBoxesCountRules()` — `nullable|integer|min:1`, unlike `removeBoxes()`'s required version) and, when given and strictly less than what remains, removes it in the same transaction as the Full→Opened transition. When `boxes_count` is omitted, `open()` just transitions Full→Opened and leaves `remaining_boxes` untouched — a worker can open a pallet without also removing boxes. A pallet already Opened can have more boxes removed later via the separate `removeBoxes()` action (409 `pallet_not_opened` if the cell isn't Opened yet, and `boxes_count` stays required there since removing boxes with no count is meaningless). Both Admin and Api/V1 controllers translate an absent or null `boxes_count` to `null` before calling `PalletActionService::open()`. Their requests share `ValidatesBoxesCount`; the private `hasEnoughBoxes()`, `decrementRemainingBoxes()` and `applyBoxesRemoval()` helpers live in `PalletActionService`, not the controllers.

The controllers delegate pallet audit writes to `PalletActionService::logCellStatus()`. For store/open/removeBoxes/transfer and product changes, `boxesCount` is the remaining count after the change. Emptying captures the remaining count **before deletion**, including the confirmed-empty path; it does not force the snapshot to zero or use the requested removal amount. Logs are snapshots, not deltas. Transfer writes two rows, one for each cell. `PalletResource.boxes_depleted_message` is a translated, non-blocking nudge (`messages.pallet_boxes_depleted`) shown whenever `remaining_boxes === 0`; `empty()` still works regardless of `remaining_boxes` since staff may empty a pallet for other reasons (damage, expiry) before every box is gone.

## confirm_empty: the mobile app decides to empty instead, not the backend
`open()` and `removeBoxes()` both accept an optional `confirm_empty` boolean (`ValidatesBoxesCount::confirmEmptyRules()`). `PalletActionService::hasEnoughBoxes()` requires `boxes_count` to be *strictly less than* `remaining_boxes` — a `boxes_count` equal to what remains is treated the same as exceeding it, not as a plain decrement, since it would fully empty the pallet and the worker may have mistyped the exact remaining count rather than meaning to empty it. So whenever `boxes_count >= remaining_boxes`: if `confirm_empty` is absent/false, it's the plain 409 `insufficient_boxes_remaining`; if `confirm_empty` is true, the service calls its private `emptyLockedPallet()` helper (also used by `emptyPallet()` and zero-count corrections). The service returns `array{pallet: ?Pallet, emptied: bool}`. The Api/V1 controller returns `response()->noContent()` (204) when emptied, otherwise a `PalletResource`, so both actions have return type `PalletResource|Illuminate\Http\Response`. The Admin actions return `RedirectResponse` through their shared action handler. Check for the emptied path before assuming a resource shape.

This means `remaining_boxes` can no longer reach exactly `0` through `open()`/`removeBoxes()` without the pallet being deleted in the same action — `PalletResource.boxes_depleted_message` (`remaining_boxes === 0`) is therefore unreachable via these two actions; it stays reachable only if a pallet's `remaining_boxes` is set to `0` some other way (e.g. directly in tests/seeders).

Deliberately, the backend does **not** proactively tell the client how many boxes remain via the 409 body — the mobile app already has `remaining_boxes` from an earlier response and is expected to compare it against the worker's input and show its own "only N remain, empty instead?" confirmation *before* sending the request, then resend with `confirm_empty: true` once approved. The 409 without `confirm_empty` is a race-condition safety net, not the primary UX path.
