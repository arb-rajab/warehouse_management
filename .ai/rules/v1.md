# V1

## Box-count tracking: open() removes boxes too; boxes_count on logs is a snapshot, not a delta
`products.boxes_count` is how many boxes make up one full pallet. `pallets.remaining_boxes` is seeded from it in `store()` and only ever decremented (never reset) via `decrementRemainingBoxes()`, guarded by a 409 `insufficient_boxes_remaining` when the request would take more than remains.

`open()` itself takes a required `boxes_count` and removes it in the same transaction as the Full→Opened transition — this was a deliberate merge (a pallet is never opened "just to be opened" in real warehouse use), not two separate calls. A pallet already Opened can have more boxes removed later via the separate `removeBoxes()` action (409 `pallet_not_opened` if the cell isn't Opened yet). Both share the `ValidatesBoxesCount` request trait and the `hasEnoughBoxes()`/`decrementRemainingBoxes()` controller helpers — don't reintroduce per-request duplication of that logic.

Every `CellStatusLog` write from this controller passes `boxesCount` = the pallet's `remaining_boxes` **after** the action (store/open/removeBoxes/empty/transfer all follow this), not the amount removed in that step — it's a running snapshot, not a delta. `PalletResource.boxes_depleted_message` is a translated, non-blocking nudge (`messages.pallet_boxes_depleted`) shown whenever `remaining_boxes === 0`; `empty()` still works regardless of `remaining_boxes` since staff may empty a pallet for other reasons (damage, expiry) before every box is gone.

## confirm_empty: the mobile app decides to empty instead, not the backend
`open()` and `removeBoxes()` both accept an optional `confirm_empty` boolean (`ValidatesBoxesCount::confirmEmptyRules()`). `PalletActionService::hasEnoughBoxes()` requires `boxes_count` to be *strictly less than* `remaining_boxes` — a `boxes_count` equal to what remains is treated the same as exceeding it, not as a plain decrement, since it would fully empty the pallet and the worker may have mistyped the exact remaining count rather than meaning to empty it. So whenever `boxes_count >= remaining_boxes`: if `confirm_empty` is absent/false, it's the plain 409 `insufficient_boxes_remaining` as always; if `confirm_empty` is true, the controller calls the shared `emptyLockedPallet()` helper (also used by `empty()`) instead of throwing, deletes the pallet, and returns a 204 — same as the plain `empty()` endpoint — instead of a `PalletResource`. Both actions therefore have a `PalletResource|JsonResponse` return type; check for the emptied path before assuming a `PalletResource` shape.

This means `remaining_boxes` can no longer reach exactly `0` through `open()`/`removeBoxes()` without the pallet being deleted in the same action — `PalletResource.boxes_depleted_message` (`remaining_boxes === 0`) is therefore unreachable via these two actions; it stays reachable only if a pallet's `remaining_boxes` is set to `0` some other way (e.g. directly in tests/seeders).

Deliberately, the backend does **not** proactively tell the client how many boxes remain via the 409 body — the mobile app already has `remaining_boxes` from an earlier response and is expected to compare it against the worker's input and show its own "only N remain, empty instead?" confirmation *before* sending the request, then resend with `confirm_empty: true` once approved. The 409 without `confirm_empty` is a race-condition safety net, not the primary UX path.
