# Components

## FilterDialog does not use Teleport
FilterDialog.vue renders its fixed-position overlay in place (no `<Teleport to="body">`), because AdminLayout has no ancestor with `overflow`/`transform` that would clip a `position: fixed` element, and Teleport would move the dialog's DOM out of the mounting component's subtree — `wrapper.get()`/`wrapper.find()` in @vue/test-utils can't see teleported content unless you query the real `document` instead, which would force every caller's test to switch from wrapper-scoped queries to `document.querySelector`. Don't add Teleport back without re-checking both constraints.

## FilterDialog moves focus in/out and traps Tab while open
FilterDialog.vue watches its `open` model: on open it stores `document.activeElement`, then (after nextTick) focuses the first focusable element inside the slot content (`contentRef`), falling back to the close button; on close it restores focus to whatever was focused before opening. Its existing document-level `keydown` listener also traps Tab/Shift+Tab between the dialog's first and last focusable elements (computed from the full dialog, header included) so keyboard focus can't leak to the page behind the overlay. Keep these refs (`dialogRef`, `closeButtonRef`, `contentRef`) if you restructure the template — the focus-trap query relies on `dialogRef`, and the "focus into content first" behavior relies on `contentRef` wrapping only the `<slot />`, not the header.

## FilterMultiSelect's (and FilterProductSelect's) panel width is capped by `usePanelMaxWidth`
Both panels anchor at their trigger's inline-start and size to content with `w-max min-w-full`/`w-max`, uncapped by a fixed `max-w-xs` — that let the panel overflow past the page's physical left edge under `dir="rtl"` for a trigger sitting near that edge (e.g. Dashboard's `PageHeader` slot, which `justify-between` pushes to the physical left in RTL). `usePanelMaxWidth(containerRef)` (lib/useDismissibleListbox.ts) caps the panel to whatever room is actually left in the direction it grows, recomputed on open. Any new dropdown built on this same content-sized-panel pattern needs the same call — don't reintroduce an uncapped `max-w-xs`.

## FilterProductSelect's panel is `position: fixed`, not `absolute`, so it can escape FilterDialog's scroll clipping
FilterMultiSelect.vue's panel is a plain in-flow `absolute` child of its trigger's `relative` container. FilterProductSelect.vue's panel used to be the same, but its option list (search + pinned + results, each with a name/id/alternate-name) is tall enough that when opened inside FilterDialog's `overflow-y-auto` content area (see below), the `overflow-y-auto` ancestor clipped/reflowed it against neighboring grid fields instead of letting it float freely. It's now `position: fixed`, with `top`/`insetInlineStart`/`minWidth` computed from the trigger's `getBoundingClientRect()` by `usePanelMaxWidth`'s `panelPosition` return value (lib/useDismissibleListbox.ts) — `fixed` positioning is clipped only by the viewport (or an ancestor with `transform`/`filter`/`perspective`, none of which FilterDialog's ancestor chain has), not by an `overflow-y-auto` ancestor, unlike `absolute`. Because `fixed` positioning doesn't track the trigger's on-screen position as its scrolling ancestor scrolls, FilterProductSelect.vue also recomputes `panelPosition` on `scroll` of the nearest scrollable ancestor and on `window` `resize` while the panel is open (removed again on close/unmount) — don't drop that tracking if you touch this component, or the panel will visually detach from its trigger when the dialog's content scrolls. If FilterMultiSelect.vue's panel is ever observed clipping the same way, switch it to this same pattern rather than re-deriving the math — `panelPosition` is already there for it to consume.

## FilterDialog has a fixed header, scrollable content, and a pinned `#footer` slot
The dialog box is `flex flex-col max-h-[90vh]`: the header is `shrink-0`, `contentRef` (wrapping the default slot) is `min-h-0 flex-1 overflow-y-auto`, and an optional `#footer` slot renders below it, `shrink-0` and outside the scrollable area — so Apply/Clear/Submit buttons stay visible no matter how tall the filter fields get. Every FilterDialog caller with action buttons (Apply/Reset/Clear, or a dialog's SubmitButton) must put them in `<template #footer>`, never inside the default slot, even if the dialog's content looks short today — a scrollable body with its actions inside it is the bug this fixes. Because the action buttons often need to submit a `<form>` that now lives in the scrollable content area (not wrapping the footer), give that form an `id` and reference it from the footer button via the native `form="<id>"` attribute (`SubmitButton.vue` takes an optional `form` prop for this) rather than nesting the footer inside the form. `$slots.footer` gates both the footer's rendering and `contentRef`'s own bottom padding, so don't add a footer wrapper with no `#footer` slot content passed to it.

## FilterMultiSelect options are role=option with Arrow/Home/End navigation
Each option `<label>` carries `role="option"` + `:aria-selected="isChecked(...)"`, and its checkbox supports ArrowUp/ArrowDown (wrapping) and Home/End to move focus between options, via `setOptionRef(el, index)` populating `optionRefs` (a plain script function, not an inline template arrow-function ref callback — Vue's ref-unwrap-in-templates rules make an inline `(el) => optionRefs[index] = el` ambiguous/wrong; always define the setter as a real function in `<script setup>` and call it from the template). Tab-based navigation and click-to-toggle still work unchanged; arrow keys are an added enhancement, not a replacement.
