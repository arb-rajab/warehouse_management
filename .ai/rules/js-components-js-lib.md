# Js Components Js Lib

## 3D map camera: full drag-based mouse-look (pitch + yaw), movement stays grid-fixed
The 3D warehouse walk has full mouse-look: dragging the pointer vertically pitches (up/down), and horizontally yaws (`stepYaw`, mapWalker.ts) — including all the way around to look directly backward. This superseded an earlier "fixed yaw, pitch-only" design (which itself briefly went through a rejected "look backward is tied to the backward movement key" variant) — both were explicitly rejected by the user in favor of standard drag-to-look, matching how `stepPitch` already worked. Yaw is NOT clamped like pitch — `normalizeYaw` wraps it into [0, 360) so it can spin freely.

WASD/arrows (`stepPosition`) are deliberately **not** relative to yaw — forward/backward always move along world Z, left/right along world X, up/down along world Y, regardless of which way the camera is currently turned. This is intentional, not a missed relative-movement feature: it keeps "forward" always meaning "deeper into the row" for the grid-navigation mental model, and lets you walk forward while looking back over your shoulder (like a real person), rather than needing a full FPS-style relative-movement system. Don't couple movement to yaw without re-confirming scope — it would also require reworking the "faced cell" probe math below. All movement/pitch/yaw/coordinate math lives in mapWalker.ts as three.js-free pure functions specifically so it's unit-testable without mocking WebGL — keep new navigation logic there, not inline in CellMap3D.vue.

The camera's actual look direction (both axes combined) is `lookDirection(pitchDegrees, yawDegrees)` — a single source of truth reused by both `updateCamera()` (in CellMap3D.vue) and `facedGridCoordinate()` (the "faced cell" panel probe, below). Changing how pitch/yaw combine into a direction only needs to happen in `lookDirection`.

**Handedness trap**: because the camera faces +Z with up=+Y, `right = up × back` (a right-handed lookAt basis, where `back` is the reverse of the forward vector) works out to world **-X**, not +X — screen-right is world -X here. `stepPosition`'s 'right' direction decreases X and 'left' increases it; this looks backwards on a first read but is correct (verified against three.js's own `Matrix4.lookAt` formula and its default-camera orientation). Getting this sign wrong is exactly the bug that shipped once already (pressing left visually moved the camera right and vice versa) — don't "fix" it back without re-deriving the handedness first, and see `stepPosition`'s doc comment for the derivation.

The camera's Y position is a free-flying value (`WalkerPosition.y`), not a fixed constant — `EYE_HEIGHT` is only the *initial*/reset eye height (`focusCell`/`resetView` set `position.y = EYE_HEIGHT`), clamped between `MIN_EYE_HEIGHT` (just above the floor) and a bit above the topmost flat (`boundsForWarehouse`'s `maxY`, which needs `maxFlatNumber` — don't drop that third argument). `facedGridCoordinate` reads the live `position.y` (not `EYE_HEIGHT`) so the "faced cell" panel still tracks the right flat while flying.

## 3D "faced cell" detail panel via facedGridCoordinate, not per-box labels
CellMap3D.vue shows full 2D-parity cell detail (label, state icon, product image/name, expiration/added-at, via a reused CellSlot.vue) for only ONE cell at a time — whichever the camera is currently "facing" — rather than labeling every box (which would be cluttered/expensive with hundreds of boxes on screen). `facedGridCoordinate()` (mapWalker.ts) projects a point one cell-spacing ahead along `lookDirection(pitchDegrees, yawDegrees)` and rounds to the nearest row/cell/flat — since yaw can now point anywhere (not just down the aisle), the probe offsets **all three** axes (row index included, not just cell/flat), so turning to face a neighboring row's aisle correctly faces a cell in that row. Its default probe distance intentionally matches `focusCell`'s standing distance so walking up to a cell via search/jump faces that same cell (and `focusCell`/`resetView` reset `yawDegrees = 0` so a jump always lands facing forward, not wherever you last dragged to). The lookup (`cellLookup`, built in `rebuildCellLookup`) is keyed by `rowIndex:cellNumber:flatNumber` and only updates the panel's ref when the key actually changes (`lastFacedKey`), to avoid a re-render every animation frame. `lastFacedKey` is force-reset on every bands rebuild so the panel refreshes its highlight/pulse/pallet content even when standing still and only the underlying data changed. CellSlot.vue is reused as-is (not duplicated) by adapting the lightweight `CellMap3DItem`/pallet-sample shape into a full fake `Cell` object (dummy `id`/`product_id`/`is_stale`, since CellSlot's template never reads those).

## Orbit camera mode reuses the walk key-handling plumbing
WASD/arrows and Space/Shift now drive BOTH camera modes — `onKeyDown`/`onKeyUp` no longer gate on `cameraMode`; `animate()` branches instead, calling `stepPosition` (walk) or the new `stepOrbitStateByKeys` (orbit: forward/backward=pitch, left/right=yaw, up/down=zoom via `Math.exp`). Don't reintroduce a walk-only key gate without re-adding a separate orbit control scheme.

Enter selects the currently-faced cell in walk mode (`onKeyDown`, reuses `facedGridCoordinate`/`selectCell`/`clearSelection`). Orbit has no "facing" concept, but Enter there is no longer a no-op either — see js-components.md for orbit's screen-center keyboard-select behavior.

Click-to-select's raycast was extracted into `cellBoxAtScreenPoint()` — reused by both `selectAtScreenPoint` (click) and the new orbit-only `updateHoverAtScreenPoint` (pointermove hover outline, `HOVER_COLOR`, reuses `getEdgesGeometry()`). Hover is cleared on pointerdown/up/cancel/blur and on leaving orbit mode.

An always-mounted (never `v-if`'d) `role="status" aria-live="polite"` `sr-only` div announces facing/selected text for screen readers, since the visual faced-cell panel is `pointer-events-none`/conditionally rendered and gives AT users no equivalent feedback.

## Cell boxes are per-state THREE.InstancedMesh, not one Mesh per cell
CellMap3D.vue's `buildCellGroup` creates exactly one `THREE.InstancedMesh` per cell state (named `'cell-box'`, allocated at the *total* cell count so any cell can move into any state without reallocating), not one `THREE.Mesh` per cell — this collapsed hundreds/thousands of individual draw calls into 3. `instancesByState`/`instanceSlotByKey` track which instance slot each cell key occupies; `placeCellInstance`/`removeCellInstance` do swap-remove insert/delete so a cell's state can change in place (`updateCellStatesAndLookup`, the fast path in `rebuildCells`) without a full rebuild. There is no per-cell `THREE.Mesh`/`userData` any more — raycasting (`cellBoxAtScreenPoint`) resolves a hit's `instanceId` back to a row/cell/flat via the state's `keys` array instead. Outlines (highlight/pulse/hover/select) are still individual `THREE.LineSegments` (rare relative to boxes), positioned via `rowWorldX`/`flatWorldY`/`cellWorldZ` directly rather than copying a mesh's `.position` (there is no such mesh any more).

`updateCellStatesAndLookup` also rebuilds `cellLookup` in the SAME pass over bands/items (previously two separate full passes — `updateCellStates` then `rebuildCellLookup`) — don't split this back into two passes for the same-cell-set fast path.
