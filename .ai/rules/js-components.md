# Js Components

## Cell-state styling is mirrored by hand in the Flutter mobile app
CELL_STATE_COLOR (lib/cellStateColor.ts) is the canonical source for cell-state visuals: empty=gray-100/gray-400 border/CircleDashed, full=green-50/green-500 border/Inbox, opened=orange-50/orange-500 border/PackageOpen (light shades; dark variants alongside). The Flutter mobile app (separate repo, not in this codebase) has its own `_getBgColor`/`_getBorderColor`/`_getStateIcon` widget methods that duplicate these same three values as Dart `Color`/`IconData` literals — there's no shared code between the two, so whenever these values change, the Dart literals must be updated by hand to match (green=full, orange=opened, gray=empty; icons: inbox/package-open/circle-dashed equivalents). The icon field was extracted from a CellSlot.vue-local map once CellMap3D.vue's state-color legend became a second real caller — see components-js-components-js-lib.md.

## ResourceFormPage supports an optional cancelHref back to the resource's index
ResourceFormPage.vue has an optional `cancelHref?: string | UrlMethodPair` prop; when given it renders a "Cancel" Link (t('common.cancel')) beside SubmitButton (wrapped together in `.flex.gap-3`, SubmitButton gets `class="flex-1"`). All four current Create/Edit pages (Rows, Users) pass their resource's `index()` action as `cancel-href`. Pass it on any new Create/Edit page using this component too, so users always have an in-app way back besides the browser back button.

## Password-confirmation mismatch shows both native validity and an app-styled FormField error
`syncConfirmationValidity()` still sets native `setCustomValidity` on `#password_confirmation` (js.md — don't remove, it's the flood guard before submit), but now also updates local `passwordValue`/`confirmationValue` refs feeding a `confirmationMismatchError` computed, bound to `password_confirmation`'s FormField `:error` prop. This makes the mismatch visible immediately with the same red-text+CircleAlert styling every other field error uses, instead of only a browser validation-bubble on submit. No server-side error exists for this key today, so this doesn't collide with backend `errors.password_confirmation`.

## Mock the whole 'three' module in CellMap3D tests — jsdom has no WebGL
jsdom can't create a WebGL context, so CellMap3D.test.ts fully mocks `three` (Scene/Group/Mesh/LineSegments/PerspectiveCamera/WebGLRenderer/geometries/materials as plain trackable classes pushed into an exported `__registry`) plus `requestAnimationFrame`/`cancelAnimationFrame`/`ResizeObserver` globals, driving the render loop manually via the captured rAF callback. Assert camera movement/pitch/highlight-outline wiring through the mock registry, not by rendering real pixels. The one thing this can't cover — an actual WebGL canvas in a real browser — is in tests/e2e/admin-cells-map-3d.spec.ts instead; don't try to make jsdom tests cover that.

## 3D scene colors are theme-unaware — overlay text needs its own opaque backdrop
CellMap3D.vue's three.js scene background/floor (setupScene: `scene.background`, floorMaterial) are fixed hex values that never adapt to the page's light/dark mode — there's no dark-mode variant of a WebGL material color. Any HTML overlay drawn on top of the canvas (the controls legend, the faced-cell panel) must therefore carry its OWN opaque, theme-aware backdrop (`bg-white dark:bg-neutral-900`, not a bare `dark:text-*` color with no background) rather than assuming a themed backdrop behind it. This regressed once already: bare `text-gray-500 dark:text-neutral-400` with no backdrop was unreadable in dark mode against the always-light floor. Use an OPAQUE background, not a semi-transparent one (`bg-white/90`) — the dark-mode contrast e2e check (`tests/e2e/admin-cells-map-3d-dark-mode.spec.ts`) reads `getComputedStyle().backgroundColor` via a canvas round-trip, which can't account for real alpha-compositing against whatever the 3D canvas is rendering beneath it.

## Dense rows alias into a jagged mess at ground level — don't fix it with fog
A realistically stocked warehouse (dozens of cells per row, several stacked flats) looks visually noisy in 3D — jagged, torn-looking geometry — when viewed from ground level down a row. This is aliasing, not a bug: dozens of small boxes (1.4 units) packed at 2.5-3 unit spacing, viewed at a shallow angle, interleave into moiré-like noise well before the far plane — confirmed by rendering only 3 boxes (clean) vs the full row (jagged) with everything else identical. Ruled out as causes: coordinate math, depth-buffer precision (tried logarithmicDepthBuffer + a tighter near/far ratio), floor plane size (tried shrinking 2000→300) — none had any effect.

A `scene.fog` was tried as the fix (fading distant clutter into the background) and **explicitly rejected by the user** — don't reintroduce it. The shipped approach instead adds real shelf-platform geometry (`addShelves()` — one `THREE.Mesh` per (row, flat) spanning that flat's actual cell range, positioned just under its boxes, named `'shelf'` so tests/tooling can filter it out from cell boxes named `'cell-box'`) so each flat level reads as a structural shelf. This measurably helps when looking down/across a row (flying up and pitching down) but does NOT fully eliminate the aliasing in the straight-on ground-level default view — that residual visual density is an accepted trade-off, not something to silently "fix" by re-adding fog or hiding geometry. If revisited, prefer reducing density directly (wider spacing constants, smaller BOX_SIZE, or fewer simultaneously-rendered flats) over anything that hides/fades content the user is meant to be able to see.

## 3D rack frame: shelves + corner posts, named for test filtering
CellMap3D.vue's rack structure has three kinds of meshes in `cellGroup`, distinguished by `mesh.name` so tests/tooling can filter them apart: `'cell-box'` (the pallets/cells themselves, colored by state), `'shelf'` (one flat platform per (row, flat) from `addShelves()`, spanning that flat's actual cell range, grouped via a per-flat `cellNumbersByFlat` map), and `'post'` (four corner uprights per row from `addPosts()` — one row-wide min/max cell range and max flat number, not per-flat — standing beside the boxes, offset by `POST_OFFSET` in X, running floor-to-topmost-shelf). Both are called from `buildCellGroup`. Their row/cell/flat-range aggregations are similar in shape but not literally shared code (different groupings: per-flat vs. whole-row) — don't force them into one shared helper unless a third consumer needs the exact same aggregation.

## 3D map touch controls: on-screen D-pad/fly buttons, gated by matchMedia
Drag-to-look already worked on touch (pointerdown/move/up are Pointer Events, which fire for touch too) — the actual gap was movement, since WASD/Space/Shift need a keyboard. Added an on-screen move D-pad + fly (up/down) button cluster (`onControlPointerDown`/`onControlPointerUp`, same `pressedDirections` Set the keyboard handlers use), shown only when `isTouchDevice` (set in `onMounted` via `window.matchMedia('(pointer: coarse)').matches`, guarded by `typeof window.matchMedia === 'function'` since jsdom doesn't implement it — tests must `vi.stubGlobal('matchMedia', ...)` and `await nextTick()` after mount, since the ref updates inside onMounted and the DOM flip is async).

Trap: these buttons are native `<button>` elements inside the same container that clears `pressedDirections` on blur (`onFocusLost`). A plain click would focus the button, blurring the container, and instantly clearing the just-pressed direction. Both `@pointerdown.stop.prevent` (preventDefault on pointerdown suppresses the browser's default focus-on-click for that pointer) and `tabindex="-1"` are required on every pad button — don't drop either when touching this code.

## DataTable columns support a `filtered` indicator icon
`Column` accepts `{ label, sortKey?, filtered? }`. When `filtered` is true, DataTable renders a small `Filter` (lucide) icon next to the header label with a `title="common.filteredColumn"` tooltip. DataTable only renders this state — the parent page computes `filtered` per column from its own reactive filter object (same split of responsibility as the existing sort arrows). When adding filters to a page with a DataTable, compute a `computed(() => ...)` per column (or group of columns affected identically) and wire it into the `columns` array's `filtered` field, rather than leaving users to guess which filters affect which columns. See Products/Index.vue and CellStatusLogs/Index.vue for the pattern.

## DataTable's column filter icon opens a quick popover, not just an indicator
Superseded the earlier "passive indicator" design. `Column` now accepts `{ label, sortKey?, filtered?, filterKey? }`. Any column with `filterKey` set always renders a clickable Filter icon (gray when `filtered` is false, blue when true) — DataTable manages a `v-model:open-filter-key` (two-way, string|null) and toggles/closes it on icon click, outside click, or Escape (same click-outside/Escape pattern as FilterMultiSelect/FilterDialog). The popover's content comes from the `#column-filter="{ filterKey }"` scoped slot, rendered by the parent page.

Multiple columns can share the same `filterKey` (e.g. Products' Full/Opened/Expired/Expiring-soon columns all use `'occupancy'`) when the backend applies those filters identically — clicking any of their icons opens the same popover.

Popover fields reuse the exact same `filters.x` v-model bindings as the main Filters dialog (duplicated markup with `popover-` prefixed ids to avoid DOM id collisions), and apply automatically on change instead of needing an Apply button: the page adds `const debouncedApplyFilters = debounce(applyFilters, 400)` (from `lib/filters.ts`) and a `watch(filters, () => { if (openFilterKey.value !== null && !filtersOpen.value) debouncedApplyFilters() }, { deep: true })` — gated so editing the same fields from the main dialog doesn't also trigger a premature auto-apply. See Products/Index.vue and CellStatusLogs/Index.vue.

## Column filter popover is positioned via JS, not CSS-anchored under the th
The popover cannot live inside the table's `overflow-hidden` wrapper (that wrapper only exists to clip the header background to the rounded corners) — nesting it there clips the popover whenever the table is shorter than the popover's height. It renders instead as a sibling of that wrapper, inside an outer `position: relative` div, positioned via an inline `:style` computed from the clicked trigger's `getBoundingClientRect()` (see `positionPopover()`/`toggleFilterPopover()`). Outside-click detection checks both the trigger button (`triggerRefs` map) and the popover element (`popoverRef`) since they're no longer nested inside one shared container. Don't revert to a plain CSS `absolute` anchor under a per-column `relative` div — that's the exact bug this fixed.

## Cell boxes update in place; per-state materials/geometry are instance-lifetime persistent
`rebuildCells()` no longer always tears down and rebuilds the whole cell group on every `bands` change. It first compares the new set of `rowIndex:cellNumber:flatNumber` keys (`bandsCellKeys`/`sameCellKeys`) against the currently-built `cellMeshLookup`: if the set of cells is unchanged (only state/highlighted/pulsing/pallet changed — e.g. a highlight-filter toggle or one cell's status update), it calls `updateCellStates()` to update each existing box's material and add/remove/recolor its outline in place, leaving shelves/posts/geometry untouched. A full `disposeCellGroup()` + `buildCellGroup()` rebuild only happens when the cell set itself changes (a row/cell/flat actually added or removed).

Box geometry (`getBoxGeometry`/`getEdgesGeometry`) and materials (`boxMaterialForState` — one shared `MeshStandardMaterial` per state, not one per box; `outlineMaterialFor` — one shared material per highlight/pulse color) are lazily created ONCE and live for the component's whole lifetime in `sceneDisposables`, disposed only on unmount — NOT recreated/disposed on every rebuild like before. Don't reintroduce per-box `new THREE.MeshStandardMaterial(...)` — reuse `boxMaterialForState(state)`/`outlineMaterialFor(kind)` instead, and don't push them into the per-rebuild `cellDisposables` array (that's only for shelf/post geometry+materials, which genuinely are rebuilt from scratch since they depend on which cells exist).

## Click-to-select works in both walk and orbit mode, not orbit-only
Click-to-select (`selectAtScreenPoint`, wired via `onPointerUpOrCancel`'s `wasSinglePointerClick`) is no longer gated to `cameraMode === 'orbit'` — clicking/tapping a box now selects it in walk mode too. This was a deliberate override of the original design (see git history / earlier `.ai/rules` note and old test name "click-to-select is orbit-only") — don't reintroduce the mode gate without re-confirming with the user first.

`displayedItem` now resolves as: orbit mode → `selectedItem` only (unchanged, orbit has no "facing" probe); walk mode → `selectedItem ?? facedItem` — a click-selected cell pins the detail panel even as the continuously-tracked `facedItem` keeps changing while you walk/look around. Selection is still cleared on every `setCameraMode` switch (a mode change resets to a fresh state in both directions).

## Orbit mode Enter now selects the centered cell — supersedes "orbit has no facing concept"
Enter in orbit mode is no longer a no-op. It now calls `selectCenteredCell()`, which raycasts from the viewport's screen center (via the shared `cellBoxAtScreenPoint`) and selects whatever cell is there, same as clicking it — giving keyboard-only users a way to select in orbit mode, since hover-outline feedback there only ever reaches a pointer. This supersedes the old note that "orbit has no facing concept, only click/hover" — walk mode still uses the true facing-direction probe (`currentFacedCoordinate`/`facedGridCoordinate`) since it has a real look direction; orbit doesn't, so screen-center is used as its keyboard-accessible equivalent instead. The orbit legend's select line now reads `cells.map.controls.orbit.selectLabel` (its own key), not the shared walk-mode `controls.selectLabel`, so its wording can mention Enter/centered-cell without also changing what the walk legend says. `cellBoxAtScreenPoint` also now raycasts against `cellMeshLookup`'s values directly instead of filtering `cellGroup.children` by name — reuse that lookup for any new screen-point hit-testing here rather than re-deriving the box list from the scene graph.
