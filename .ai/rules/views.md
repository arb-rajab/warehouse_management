# Blade dark mode and user-authored HTML sanitization

## Dark mode is prefers-color-scheme only
No `$appearance` prop is shared to any view, and `resources/css/app.css` defines no `@custom-variant dark`, so every `dark:` utility resolves to the `prefers-color-scheme` media query. The starter kit's `@class(['dark' => ($appearance ?? 'system') == 'dark'])` on the `<html>` tag was removed because nothing populated `$appearance` — do not re-add it without also adding the middleware that shares the value. `tests/e2e/login-dark-mode.spec.ts` covers dark mode via Playwright's `emulateMedia({ colorScheme: 'dark' })`.

## User-written HTML is printed with clean_html(), never raw
A product, classified or digital-product description, support-ticket details or replies, and anything else a seller or customer writes as HTML, is printed as `{!! clean_html($x) !!}` (App\Services\HtmlSanitizer). A raw `{!! !!}`, `@php echo` or `<?php echo` of such a field is stored XSS: the admin ticket page ran a customer's script in a staff session. Admin-written content (CMS pages, settings texts) is trusted and printed as it is. The converted writers clean it before storing it instead: blog posts, whose public page also prints `clean_html($blog->description)` (.ai/archive/store-backoffice/changes-20261013.md §18), and the footer, appearance and custom-page rich text, whose raw storefront prints (cookie text, custom and policy pages) are unchanged (§20). `HtmlSanitizerTest`'s scan fails on a new raw print of `->details`, `->reply`, `->description` or `getTranslation('description')` that is not wrapped.

## Storefront identity: Direction A tokens in the storefront-only stylesheet
The public storefront's look is Direction A ("Souq", docs/identity-proposal/README.md while that folder exists): brand red `#C4170C`, saffron accent `#F2A900`, warm ink/paper neutrals, danger `#B42318`, IBM Plex Sans Arabic for both scripts and IBM Plex Mono for codes. It lives in `resources/css/storefront.css`, its own Vite entry, which `shop/frontend/layouts/app.blade.php` loads with `@vite` after `aiz-core.css` (plus a preload of the Plex Latin, and on Arabic pages Arabic, 400 file). The fonts are self-hosted through `@fontsource/ibm-plex-sans-arabic` and `@fontsource/ibm-plex-mono`, so the Blade CSP needs nothing new; never add a Google Fonts link. The sheet defines the tokens, maps the theme's own variables (`--primary`, `--hov-primary`, `--dark`, `--light`, `--secondary`, `--success`, `--warning`, `--danger`, `--info`, `--soft-*`) onto them and overrides the shell (strip, header, category bar, cards, buttons, forms, footer, pagination, modals). Override the theme there, never fork `public/assets/css/*`, and keep every rule direction-neutral (logical properties or a `[dir='rtl']` override) because Arabic still loads `bootstrap-rtl.min.css`. Legacy SVG icons keep their `fill="#..."` attributes; the sheet remaps the theme's red, saffron, blue and greys by attribute selector, so prefer `fill="currentColor"` in new markup and never add a hex colour in an inline `style`.

The `base_color` / `base_hov_color` website settings are retired as the colour driver: the admin Appearance form still stores them, but no storefront page prints them (the old inline `:root` block is gone). The header's brand name is the placeholder `messages.brand_name` (lang/{en,ar}/messages.php), next to the logo; the owner replaces it there. The back office (WMS and store control panel, `resources/css/app.css`, `resources/js/**`) does not load this sheet and is not restyled by it. `tests/Feature/StorefrontIdentityTest.php` covers the stylesheet, fonts, brand name and the absent override in both languages.
