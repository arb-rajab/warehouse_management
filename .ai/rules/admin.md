# Admin

## Shared filter-dialog scaffolding lives in lib/filters.ts
`resources/js/lib/filters.ts` exports `filterSectionHeadingClass` (the filter-dialog section heading Tailwind classes), `filterTriggerButtonClass`/`filterClearButtonClass` (the dialog's trigger/clear buttons), `fieldLabelClass` (the filter-field label), `countBadgeClass` (the small rounded-pill count badge — blue, not the page's usual gray-900/white pairing, so it stays visible on a selected/dark background), and `columnNumberOptions(maxColumnNumber)` (builds the 1..N column dropdown options). `Cells/Index.vue` and `CellStatusLogs/Index.vue` both import these instead of redefining them locally — import `filterSectionHeadingClass` aliased as `sectionHeadingClass` to keep the template unchanged. `countBadgeClass` is used for both the highlight-filter trigger's active-filter count (CellHighlightFilters.vue) and the cell map's per-flat/total highlight-match counts (Cells/Index.vue — see controllers-admin.md). Reuse these in any future admin listing page with a filter dialog instead of re-copying them.

The toggle-sort-direction-then-reapply logic behind a sortable DataTable column is `lib/filters.ts`'s `toggleSort(filters, key)` export, shared by `CellStatusLogs/Index.vue` and `Products/Index.vue` (extracted once the second sortable admin listing appeared). A future sortable admin listing should import it too, rather than re-inlining a local copy.

## filterSectionHeadingClass is the shared admin section-heading style, not just filter dialogs
`resources/js/lib/filters.ts`'s `filterSectionHeadingClass` export is reused for any admin section heading with this look, not only filter-dialog sections — `Dashboard/Index.vue` imports it (aliased as `sectionHeadingClass`) for its occupancy/expiring/activity section headings, same as `Cells/Index.vue` and `CellStatusLogs/Index.vue` do for their filter-dialog sections. Don't redeclare the class string locally in a new admin page; import and alias it instead.

## A new admin-facing feature/screen needs its own Help/ sub-page and a "?" icon, in the same change
This app has an in-app, non-technical help section for admin-panel users, separate from the developer-facing README/CLAUDE.md/`.ai/rules` docs: `routes/web.php`'s `admin.help.index` (`GET admin/help`, `HelpController::index`) and `admin.help.show` (`GET admin/help/{topic}`, `HelpController::show`, `{topic}` bound to the `App\Enums\HelpTopic` backed enum), rendering `resources/js/pages/Admin/Help/Index.vue` (the topic-picker landing page) and one static, no-backend-props page per topic. The topic set covers every top-level admin screen, one enum case/page each: `dashboard` (Dashboard.vue), `rows` (Rows.vue), `cells` (Cells.vue — the warehouse map), `cell-logs` (CellLogs.vue), `cell-verification-rounds` (CellVerificationRounds.vue), `products` (Products.vue), `users` (Users.vue). Every one of those admin screens links to its matching topic via the shared `components/HelpLink.vue` ("?" icon) placed in its `PageHeader` slot — see `Dashboard/Index.vue`, `Rows/Index.vue`, `Cells/Index.vue`, `Users/Index.vue`, `Products/Index.vue`, `CellStatusLogs/Index.vue`, `CellVerificationRounds/Index.vue`.

**Whenever a new admin-facing feature/screen is added to this app, add its corresponding `Admin/Help/<Topic>.vue` sub-page (in plain, non-technical language) plus a `HelpLink` "?" icon on the new screen deep-linking to it (add a new `HelpTopic` case + route/controller branch, since it's a genuinely new top-level topic) — in the same change that adds the feature, not as a follow-up.** A sub-screen of an existing topic (e.g. a new tab/dialog on an already-covered page) extends that topic's existing help page instead of getting its own `HelpTopic` case. When help content needs to describe something that already has a single source of truth elsewhere in the app (e.g. cell-state colors/labels), reuse that source rather than duplicating hardcoded values that could drift from the real UI — see the shared `components/CellStateLegend.vue`, built from `lib/cellStateColor.ts`'s `CELL_STATE_COLOR`/`CELL_STATES`/`cellStateLabel` and reused by both `Help/CellLogs.vue` and `Help/Cells.vue` (extracted once the second consumer needed the same legend).

## Help pages show the real button/control, not just its name in prose
A help page referencing a specific button/badge/control ("click the Add row button") renders that control too, not only its name as text — see every `Admin/Help/*.vue` page. Wrap the *real* component or an exact copy of its markup/classes in the shared `components/HelpUiPreview.vue` (a dashed-border, `pointer-events-none`, `aria-hidden="true"` box) so it's visually a non-interactive preview rather than a second live control competing with the actual one elsewhere on the page; also add `tabindex="-1"` to the wrapped interactive element itself so it can't steal keyboard focus. Source the preview's label/text from the same i18n key the real control uses (e.g. `t('rows.index.addRow')`), never a re-typed string, so the preview can't drift from the real button's wording. When the same preview is needed on a second page, extract it as its own component the way `components/UserRoleBadge.vue` was pulled out of `Users/Index.vue`'s role-badge markup once `Help/Users.vue` needed to render the identical badge — don't recreate the class string a second time.

This applies just as much when the prose describes filling in a form or opening a dialog, not just naming a single button — the form/dialog's actual fields need a preview too, not only the trigger that opens it (see `Help/Rows.vue`'s creating/editing sections previewing `RowFormFields`, `Help/Users.vue`'s accounts section previewing `UserFormFields`, `Help/Cells.vue`'s managingPallets section previewing each pallet-action tab's fields, and `Help/CellLogs.vue`'s filtering section previewing the real `FilterProductSelect`/`LocationFilterFields`/`CellLogActivityFilterFields`/`DateRangeFilterFields`). `components/FilterDialog.vue` is a full-viewport `fixed inset-0` overlay, not a Teleport — never wrap its outer chrome in a preview, since it would hijack the whole help page as a fake modal. Preview only the dialog's *inner* fields, reusing the same field-level components/classes the real dialog uses (`FormField`, `RowFormFields`, `UserFormFields`, `FilterNumberField`, `FilterDateField`, `FilterProductSelect`, `FilterMultiSelect`, `fieldLabelClass`/`plainFieldInputClass` from `lib/filters.ts`), with a plain `<p class="text-lg font-semibold">` sub-heading sourced from the dialog's own `:title` key when a labelled frame helps readability (matches `FilterDialog.vue`'s own `<h2>` style without reusing its overlay markup).

A multi-field form/dialog preview can't be made non-interactive by adding `tabindex="-1"` to each nested control one at a time the way a single button/badge preview does — many of the reusable field components (`FilterMultiSelect`, `FilterProductSelect`, `FilterDateField`, `FilterNumberField`, `RowFormFields`, `UserFormFields`, `LocationFilterFields`, `CellLogActivityFilterFields`, `DateRangeFilterFields`) render their real interactive element (a `<button>`/`<input>`) *inside* their own root, so an attribute passed to the component tag lands on that wrapper root instead (Vue's default attrs fallthrough), never reaching the control. Add the plain HTML `inert` attribute to the `<HelpUiPreview>` tag instead (`<HelpUiPreview inert class="mt-2 block">`) — it's a global attribute, so Vue always renders it as a static attribute on `HelpUiPreview`'s own root `<span>` regardless of what's nested inside, and `inert` disables focus/pointer/accessibility-tree presence for the *entire* subtree no matter how deeply the real control is nested. This supersedes per-element `tabindex="-1"` for these composite-component previews; a single-root, single-control preview (`AddResourceLink`, `TableActionLink`, `DashboardStatTile`) still uses `tabindex="-1"` directly since its root *is* the control.

`RowFormFields.vue` takes an optional `idPrefix` prop (default `''`, prefixing `letter`/`cells_count`/`flats_count`) for the same reason `LocationFilterFields.vue` already has one — so a page can render it more than once (e.g. `Help/Rows.vue`'s separate creating/editing previews) without a duplicate-DOM-id collision. Give any shared form-fields component the same treatment before rendering it twice on one page.
